# Al-Khair — Architecture (Phase-Zero Plan)

> **Status:** Planning document. No code exists yet. Nothing here introduces a field, screen,
> role, or collection that is not defined in Chapter Four or Chapter Five. Every artifact traces
> to a source table or figure.

## 1. Architectural style

- **Feature-First + simplified Clean Architecture.** Each feature owns three layers —
  `data/` (Firestore/remote sources, DTOs, repository implementations), `domain/` (entities,
  repository interfaces, use-cases where warranted), `presentation/` (Riverpod providers,
  screens, widgets). No feature reaches into another feature's layers; shared UI lives in
  `features/shared_widgets/`, shared infrastructure in `core/`.
- **Single Flutter codebase, two builds** (resolved decision): donor + volunteer ship as the
  **mobile** build; charity-admin screens (6–12) are **responsive** and ship as a **Flutter Web**
  build (satisfies FR10 "web-accessible dashboard", Deployment Diagram Fig 4.11). Role-based
  routing gates which surface a signed-in user sees.
- **Back end is the single source of truth** (Ch.4 §4.3.4). Apps never talk peer-to-peer; every
  interaction is mediated by Firebase. Maps is a side-call for rendering/routing only.

## 4. Data-flow per role (UI → Firestore and back)

**Auth (all roles — username+password, no phone/OTP verification, item 18):**
```
SignUpScreen → RegistrationController.createFromSignUp(SignUpData)
  → AuthRepository.checkPhoneRegistered(phone)  [plain uniqueness check]
    → createUserWithUsernamePassword → FirebaseAuth.createUserWithEmailAndPassword → uid
      → createUserProfile(role) [+ completeVolunteerRegistration for volunteers]
        → authStatusControllerProvider loads Users(+Volunteers) → deriveAuthStage(...)
          → GoRouter redirect (authRedirect) sends the user to their area:
              role=donor        → /donor/home
              role=volunteer     → VolunteerExtraStepScreen: pending view
                                   (Volunteers.approval_status=pending) until approved
              role=charity_admin → /admin/dashboard
Claims: onUsersWrite / onVolunteerWrite (Cloud Functions) mirror role +
  approval_status + charity_id into custom claims and write claims_updated_at;
  the client force-refreshes its token. Firestore Rules remain authoritative.
```

**Donor (report + track):**
```
DonorReportScreen → reportControllerProvider (Riverpod)
  → DonationRepository.submit(dto)  [client validation first]
    → FirestoreService.create('DonationReports', ...)   (safety_confirmed, latitude/longitude via geolocator FR3)
      → [onDonationReportCreated trigger] finds nearby approved volunteers (Haversine,
        current_lat/lng, DISPATCH_RADIUS_KM) → writes Notifications (FR6). FCM push is
        deferred — see the Phase 4 note below.
Back: Firestore stream → statusProvider → DonorStatusScreen progress tracker + Notifications feed (FR5)
```

**Volunteer (alert → navigate → confirm) — built in Phase 4:**
```
openReportsProvider (Firestore stream of status=='reported') → VolunteerAlertScreen (FR6)
  accept → DonationRepository.acceptReport(reportId, volunteerId)
    → client-side Firestore transaction, guarded by firestore.rules' claim rule
      (reported→assigned, volunteer_id==self, prior volunteer_id==null) (FR7)
  → VolunteerNavScreen: embedded google_maps_flutter route (straight line) +
    offline Haversine distance/ETA header, "Start navigation" → native maps app
    handoff via url_launcher for real turn-by-turn (FR8 — see the Fig 5.5 vs FR8
    note below)
  confirm collection → status=collected ; confirm delivery → status=delivered (FR9)
    — each a guarded transaction, rules restrict to the assigned volunteer only
Back: Firestore streams update donor + admin views in real time (FR11, FR13).
```

**Phase 4 note — Fig 5.5 vs FR8's "turn-by-turn" wording:** Chapter Five §5.2.3 describes Screen 5
as a route line with a distance/ETA header and two confirmation buttons — it does not depict an
in-app turn-by-turn maneuver engine. Reimplementing one would duplicate Google's own navigation
product for no benefit. FR8 is satisfied literally by the "Start navigation" handoff to the
device's native Google Maps app (real, voice-guided turn-by-turn); the embedded map matches Fig
5.5 exactly for in-app context. This resolution was confirmed with the project owner before
Phase 4 implementation.

**Phase 4 note — FCM deferred, reassignment/timeout split into Phase 4b:** Chapter Four §4.3 names
Firebase Cloud Messaging, but no `fcm_token` field exists in the data dictionary (Tables 4.2–4.8)
— adding one now would be an undocumented schema change, the same violation class as the earlier
dropped `Donors` sub-collection (§6.2). Phase 4 drives Screen 4 from a live Firestore stream of
`Notifications`/open reports instead, which satisfies FR6's real-time intent while the app is
foregrounded; real FCM push + token storage are deferred to when Track B (real Firebase deploy)
unblocks and the token field can be documented properly. Separately, Fig 4.5's reassignment/
timeout activity ("not accepted in time → reassign to next-nearest volunteer → after 3 attempts →
flag for admin review") is **out of Phase 4's scope** — it needs an undocumented attempt-counter
field, an undocumented timeout duration, and scheduled infra the local emulator doesn't exercise
cleanly. It is deferred to **Phase 4b**, once those fields and the timeout value are decided and
documented; the `reported→expired` rule transition already exists in `firestore.rules` reserved
for that work.

**Charity Admin (dashboard + approvals + reports):**
```
AdminDashboard ← Firestore streams of DonationReports scoped by charity_id (FR11)
VolunteerApprovalScreen → set approval_status=approved|revoked (FR10)  [claims: charity_admin only]
ReportsDirectory → generateReport() → [Cloud Function] aggregates DonationReports into Reports (FR12)
  → Monthly/Category/Volunteer-performance views → PDF export (Screen 12)
```

Maps is a direct side-call from the volunteer app to Google Maps Platform (Fig 4.2 / 4.11); it
never touches Firestore.

## 6. Recorded design decisions (see SECURITY.md for full auth detail)

1. **Unified Phone Auth + OTP** for all roles; Figure 5.1 "password" field = OTP code entry.
   `password_hash` (Table 4.2) is unused by the app.
2. **7 collections only** — no `Donors` collection; donor = `Users` doc with `role=donor`, no
   sub-doc. Class-diagram `donorType`/`address` dropped (absent from ERD + data dictionary).
3. **One responsive codebase**; admin on Flutter Web.
4. **Assumptions** (also in SECURITY.md): server-side proximity dispatch (Cloud Function on
   `DonationReports` create using `current_lat/lng`); server-side `Reports` aggregation; status
   UI labels map onto the canonical enum `reported|assigned|collected|delivered|expired`; only
   `AlKhair_Logo_Icon_1024.png` is present (full lockup absent — Phase-1 asset gap).
5. **Phase-2 flagged assumptions** (no documentation covers these; recorded rather than guessed
   silently, same treatment as the Phase-1 Cairo-font note in §7):
   - **`vehicle_type` (Table 4.3)** — Chapter Four/Five give no enumerated set of vehicle types,
     so the volunteer extra step uses a **free-text field** (stored as a string) rather than an
     invented enum. Implemented in `volunteer_extra_step_screen.dart`.
   - **Volunteer pending-approval view** — none of the 12 documented screens covers a volunteer's
     post-registration *pending* state (Fig 5.4 is the alert screen for **already-approved**
     volunteers, not this). Per the Screen-1 precedent (§5 note), the pending/revoked view is
     **folded into `volunteer_extra_step_screen.dart`** (same `Routes.volunteerExtra` family), not
     added as a new screen. The `AuthStage.volunteerPending` guard targets that same route.
   - **`charity_id` at registration** — the volunteer **selects** their charity from the seeded
     `Charities` list at the extra step; `charity_id` is written at create and is immutable
     thereafter (forced by the already-approved `firestore.rules`). `Charities` is seeded with the
     real charity from Fig 5.6, «جمعية البر بمحافظة بيشة» (see `functions/scripts/seed_charities.js`).
6. **Phase-4 flagged assumptions** (Volunteer module, Screens 4 & 5 — FR6–FR9; confirmed with the
   project owner before implementation, same treatment as items 4–5 above):
   - **Dispatch scope: FR6–FR9 only, no in-phase reassignment.** Fig 4.5's "not accepted in time →
     reassign to next-nearest volunteer → after 3 attempts → flag for admin review" is an explicit
     decision point with no built precedent, an undocumented attempt-counter field, and an
     undocumented timeout duration — split into **Phase 4b** rather than silently included as a
     partial version or silently dropped. See the Phase 4 note above §5.
   - **FCM deferred; Screen 4 driven by a Firestore stream.** No `fcm_token` field exists in the
     data dictionary; adding one now would be an undocumented schema change. Real push moves to
     when Track B unblocks. See the Phase 4 note above §5.
   - **Dispatch radius: 10 km default**, mirrored by hand between the Dart constant
     (`kDefaultDispatchRadiusKm`) and the Cloud Function's `DISPATCH_RADIUS_KM` — the two runtimes
     can't share a constant (same treatment as `MAX_QUANTITY`/`kMaxDonationQuantity`).
   - **Proximity matching is in-memory Haversine** over approved volunteers with a known
     `current_lat/lng` — Firestore has no native geo-range query for this shape; acceptable at this
     project's scale.
   - **Accept is a client-side Firestore transaction**, not a callable — `firestore.rules`' claim
     rule (reported→assigned, `volunteer_id==self`, prior `volunteer_id==null`) already makes it
     race-safe via Firestore's optimistic concurrency, so no server-side rate-limit-style logic is
     needed the way Phase 3's report creation required one.
   - **Decline is a local-only dismissal** — no Firestore write, no rule path; the report simply
     stays open for another volunteer, which is exactly what the Phase 4 rules tests assert.
   - **Screen 5's distance/ETA is offline Haversine**, and the embedded map draws a straight
     point-to-point line rather than a real Directions-API polyline (needs network + a live Maps
     key) — see the Fig 5.5 vs FR8 note above §5 for the navigation-fidelity resolution.
7. **First-time-region deploy gotcha: silent missing Cloud Run invoker bindings** (encountered
   during the `alkhair-bisha-dev` production consolidation, functions relocated to
   `europe-west1` — see the region-migration entry below). The **first** `firebase deploy
   --only functions` attempt against a brand-new region hung for ~90 minutes with no progress
   (killed and retried) before a second attempt reported full success for all 5 functions. That
   success was misleading: `gcloud run services get-iam-policy` afterward showed **4 of the 5**
   underlying Cloud Run services (`createDonationReport`, `onUsersWrite`, `onVolunteerWrite`,
   `onDonationReportCreated` — everything created during the recovered/retried deploy) had an
   **empty IAM policy**, meaning neither the public `allUsers` invoker (required for `onCall`
   callables — the function code, not Cloud Run IAM, is the real Firebase Auth boundary) nor the
   Eventarc push subscription's service account (`{project-number}-compute@developer
   .gserviceaccount.com`, required for the 3 Firestore-trigger functions) could actually invoke
   them. Only `generateReport`, deployed cleanly on the very first attempt before the hang, had
   its binding. Symptom: a donor's report submission failed with a generic Cloud Run 401
   ("access token could not be verified") surfaced client-side as the generic Arabic
   unexpected-error message, and — more seriously — the Firestore-trigger functions would have
   silently never fired at all (no error, just no dispatch) had this gone unnoticed. **Root
   cause is very likely the same underlying issue as the 90-minute hang**: Cloud
   Functions/Cloud Run/Eventarc service-identity and IAM-binding propagation for a project's
   *first-ever* deploy into a given region is not instantaneous and not always retried/reported
   correctly by `firebase deploy`, which can report a misleading "successful create operation"
   before all of a function's supporting IAM state has actually converged. **Fix:** manually
   applied the missing `roles/run.invoker` bindings via `gcloud run services
   add-iam-policy-binding` (one `allUsers` binding for the `onCall` callable, three
   compute-service-account bindings for the Eventarc-triggered functions) after confirming no
   org policy (`iam.allowedPolicyMemberDomains`) was blocking it. **Flag for Chapter Six:** a
   second real, undocumented-in-advance infrastructure constraint hit during production
   deployment, alongside the `me-central2` data-sovereignty sales-gating issue — worth reporting
   together as evidence that first-time regional Google Cloud deploys need an explicit
   post-deploy IAM-policy verification step, not just a green `firebase deploy` exit code.
8. **`firestore.indexes.json` was empty for the project's entire history — a real gap, fixed, not
   just a migration patch.** Four collection queries have always required composite indexes:
   `DonationReports` filtered by `donor_id`/`status`/`volunteer_id`, each ordered by
   `created_at` (`firebase_donation_repository.dart`), plus `Notifications` filtered by
   `user_id` ordered by `created_at`. These indexes existed only as an **undocumented,
   console-created artifact** on the old `me-central2` database (almost certainly built by
   clicking the auto-generated "create index" link the first time this exact error was hit
   during the Phase 7 manual E2E) — never captured in the repo, so deleting/recreating the
   database for the `europe-west1` migration silently dropped them. Symptom: the donor status
   screen (and, unfixed, the volunteer-alert and volunteer-nav screens next) showed a generic
   "تعذّر تحميل البلاغات" failure — the report/notification writes themselves succeeded, only
   the indexed reads failed. **Fix:** all 4 composite indexes are now defined in
   `firestore.indexes.json` and deployed via `firebase deploy --only firestore:indexes`, so this
   requirement is reproducible from a clean project going forward instead of depending on a
   one-off console click nobody would think to redo. Composite index builds are asynchronous
   (`CREATING` → `READY`, a few minutes) — verified via `gcloud firestore indexes composite
   list` before re-testing, rather than assuming the deploy's success message meant the indexes
   were immediately queryable.
9. **Consolidation to a single real Firebase project, `alkhair-bisha-dev`, for final production
   testing and demo recording.** The project had drifted across two real Firebase projects
   (`alkhair-bisha-dev`, `alkhair-bisha-prod`) plus the emulator-only `demo-alkhair`, wired
   through Flutter dev/prod product flavors — repeated project-ID confusion in the final phase,
   for no real benefit (`alkhair-bisha-prod` never had an iOS app registered; iOS already ran
   only against dev).
   - **Merged:** `alkhair-bisha-dev` is now the sole real project. `alkhair-bisha-prod` is
     **abandoned but not deleted** (deletion deferred to post-submission) — simply de-referenced
     everywhere (`.firebaserc`, `firebase.json`, `firebase_options.dart`).
   - **Flavor collapse:** dev/prod Flutter product flavors, `main_dev.dart`/`main_prod.dart`, and
     the `kFlavor`/`kIsProduction` constants are gone. A single `lib/main.dart` entrypoint and one
     standalone `kUseEmulator` switch (`--dart-define=USE_EMULATOR`, default `true`) now control
     everything. Android ships as the single package `com.alkhair.alkhair_app.dev`.
   - **App Check — explicit one-time-demo scope decision, not an oversight:** the app now
     activates **debug providers only** (`AndroidProvider.debug`/`AppleProvider.debug`)
     unconditionally, including for the real-cloud production demo. Real attestation (Play
     Integrity / App Attest) was in scope conceptually but is out of scope for this one-time
     graduation demo; SECURITY.md §5's hard-enforce-before-Phase-2 language is superseded by this
     decision for the remainder of the project.
   - **`demo-alkhair` retained**, deliberately, as the offline emulator/test layer — automated
     Jest suites (`test:rules`/`test:functions`), seed scripts, and emulator-start docs still use
     it. Only `.firebaserc`'s `default` project changed (→ `alkhair-bisha-dev`), so a bare
     `firebase deploy` can no longer land on the wrong project by accident.
   - **Region deviation (the region-migration entry referenced by item 7 above):** Chapter
     Four's KSA data-residency intent specified `me-central2` (Dammam) for both Firestore and
     Cloud Functions. This could not be realized: (a) `me-central2` is **sales-gated** for Cloud
     Functions/Cloud Run/Eventarc, requiring a Google data-sovereignty sales agreement not
     obtainable before the submission deadline (confirmed via a direct `generateUploadUrl` REST
     call returning `LOCATION_POLICY_VIOLATED` after Blaze billing and all required APIs were
     already enabled with zero blocking org policies); and (b) Firestore *direct-event* Eventarc
     triggers hard-require the trigger and database to be in the **same single-region location**
     — confirmed against Google's Eventarc locations documentation, not assumed — so compute
     could not simply move to an ungated region while leaving the database in `me-central2`.
     **Both Firestore data-at-rest and Cloud Functions compute were therefore relocated to
     `europe-west1`** (the empty `me-central2` `(default)` database was deleted and recreated in
     `europe-west1`, confirmed empty via `listCollectionIds` before deletion — no data lost). The
     region is now a single source of truth: `functions/src/region.ts` on the backend,
     `lib/core/providers/firebase_providers.dart` and `lib/bootstrap.dart` on the client. **Flag
     for Chapter Six:** report this as a documented **external infrastructure constraint** (a
     Google Cloud commercial/regulatory gate reachable only via a sales agreement, plus a
     platform-level Eventarc co-location requirement), not a design or quality shortcut — the
     Chapter Four data-residency intent was correct and implementable in principle, just not
     reachable inside the project's timeline.
   - **Verified end-to-end against the final real-cloud configuration:** the full donor → dispatch
     → volunteer accept/collect/deliver → donor tracker → admin dashboard journey was re-run
     against `alkhair-bisha-dev`/`europe-west1` after the migration (three separate report
     submissions, all reaching `delivered`), including direct confirmation via Cloud Functions
     logs that `onDonationReportCreated` actually fires in `europe-west1` off the `europe-west1`
     database — the specific mechanism this migration depended on working.
10. **Removed unused `l10n`/`.arb` codegen scaffolding** (`l10n.yaml`, `lib/l10n/app_ar.arb`,
    `lib/l10n/app_localizations*.dart`, `generate: true`) — never wired into `MaterialApp`
    (`bootstrap.dart` only uses `GlobalMaterialLocalizations`/`GlobalWidgetsLocalizations`/
    `GlobalCupertinoLocalizations` delegates directly), and NFR4 only requires a single fixed
    Arabic UI, not runtime locale switching. `flutter_localizations` itself is retained (still
    needed for those Global delegates — RTL/date-picker/Material-widget support). This also fully
    sidesteps the Windows synthetic-package `gen_l10n` bug (flutter/flutter#162936) rather than
    working around it.
11. **Android manifest location-permission parity gap, fixed.** `AndroidManifest.xml` had zero
    `<uses-permission>` entries — the Android counterpart of the Phase 7 iOS
    `NSLocationWhenInUseUsageDescription` fix was never mirrored, since all prior E2E testing ran
    on iOS Simulator only. `ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION` added; both donor report
    submission (FR3) and the volunteer manual "تحديث موقعي" refresh (Phase 7 Part A1) share the
    same `GeolocatorLocationService`, so one fix covers both call sites. Regression-guarded by
    `test/android_manifest_test.dart` (asserts the manifest text contains both permission strings —
    the mocked-`LocationService` unit tests can't otherwise catch a missing native manifest entry).
12. **Shared debug-only signing keystore, `android/debug.keystore`, committed.** Previously every
    teammate's machine auto-generated its own unique debug certificate, so Firebase rejected real
    (non-test) phone-number sign-in with `app-not-authorized` unless each machine's SHA-1/SHA-256
    was individually registered in Firebase Console. A single keystore (standard debug credentials
    — `storePassword`/`keyPassword` "android", alias `androiddebugkey` — the universal Android
    debug-key default, not a secret) is now committed and wired via an explicit
    `signingConfigs.sharedDebug` in `android/app/build.gradle.kts`, used by the `debug` buildType
    only. **Deliberately not reused by `release`**, which keeps AGP's own machine-local default
    `debug` signingConfig — committing this file for team debug-build convenience must not also
    widen what a real release APK can be signed with.
13. **iOS/Android native-config parity, audited and closed out as a category** (three gaps hit
    this session alone, all traceable to the same root cause: every prior E2E run was on iOS
    Simulator only, so Android-only native-config gaps went undetected until an actual Android run
    would have crashed). Fixed:
    - **Location permission crash** — `AndroidManifest.xml` had zero `<uses-permission>` entries;
      Android counterpart of the Phase 7 `NSLocationWhenInUseUsageDescription` fix, never mirrored.
      `ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION` added (covers both donor report submission
      and the volunteer manual location refresh — same shared `GeolocatorLocationService`).
    - **Maps SDK key crash** (`IllegalStateException: API key not found`) — Android had no
      `com.google.android.geo.API_KEY` meta-data at all. Added, sourced from a new gitignored
      `env/android_secrets.properties` (never committed), substituted via
      `manifestPlaceholders["MAPS_API_KEY_ANDROID"]` in `android/app/build.gradle.kts` — **not**
      copied from iOS's actual (broken) pattern; see the flagged item below.
    - **Missing `INTERNET` permission** — found during the audit, not requested by name. Neither
      `firebase_core` nor `google_maps_flutter_android`'s own plugin manifests declare it (checked
      directly in `pub-cache`), and the app's own manifest never did either. Without it, every
      Firebase network call and all Maps tiles would fail on Android — iOS needs no Info.plist
      equivalent (HTTPS access is sandboxed-default). Added.
    - Regression-guarded by `test/android_manifest_test.dart` (checks manifest text for all three).
    - **Confirmed as needing no Android counterpart** (asymmetric by platform architecture, not an
      oversight): `CFBundleURLTypes`'s Firebase-generated URL scheme (iOS-only phone-auth
      reCAPTCHA-callback requirement — Android's Firebase Auth SDK uses Play
      Integrity/SafetyNet instead, no custom scheme; confirmed no Google Sign-In/deep-link code

15. **Username + password replaces Phone/OTP as the login method — supervisor-directed
    architectural change, supersedes item 1 above.** OTP is now a **sign-up/reset verification
    step**, not the login mechanism itself.
    - **Final flow:**
      - **Sign-up** (one form: username, password, name, phone, role [donor/volunteer only —
        see below], plus volunteer-only email/vehicle_type/charity): on submit, **no Firebase
        Auth account or Firestore doc is created yet** — the form is held in memory only, and an
        OTP is sent to the phone via the existing (unmodified) `requestOtp`/OTP-screen mechanism.
        Only on OTP success: the chosen username+password is **linked** onto the OTP-verified
        phone-auth account (`linkWithCredential`, not a second account — Firebase OTP inherently
        signs in a phone-auth user, so linking avoids orphaned accounts), then the `Users` doc is
        created with `phone_verified: true` baked in from creation (there is no unverified-account
        state to manage — if OTP fails/expires/is abandoned, no account and no doc exist; the user
        just restarts sign-up).
      - **Login**: username + password only, no OTP. Firebase has no native username provider, so
        username maps to a synthetic email `{username}@alkhair-app.internal` (never shown in UI)
        for `signInWithEmailAndPassword`/the sign-up-time link. Firebase's own
        `email-already-in-use` on link is the duplicate-username check — surfaced only **after**
        OTP succeeds, never before (case 7 below).
      - **Forgot password** (reuses the phone already on file — never re-entered): the user
        enters only their username; a new callable, `lookupPhoneForUsername` (Admin SDK query,
        since Firestore rules only allow reading one's own `Users` doc and an unauthenticated
        client can't query by username directly), returns the phone or null. Unknown username →
        generic "if this account exists…" message, no OTP sent, no navigation (avoids username
        enumeration in the UI — though the callable's own response necessarily differs
        found-vs-not-found, since the client needs the real number to call `requestOtp`; full
        mitigation would need server-side SMS sending, out of scope). Known username → OTP sent
        to that number, reusing the **same OTP screen component**, branched by `flowMode` to a
        "set new password" completion instead of account creation. Re-authenticating via OTP
        signs back into the *same* uid (the phone was linked to it at sign-up), so
        `updatePassword` is called — no `linkWithCredential`, this is a reset, not account
        creation. A `passwordResetInProgressProvider` flag overrides the router's normal stage
        derivation for the whole flow — without it, an *existing* user's OTP re-auth would
        redirect them straight to their home screen (their `Users` doc already exists) before
        they ever set a new password.

17. **Item 16's bug-2 fix was real but incomplete — a second, independent cause of the same
    symptom (sign-up never reaches the OTP screen) was found on real-SMS devices (iPhone
    simulator, macOS), reproduced fresh with a new phone number, no duplicate-phone involved.**
    - **Root cause:** `FirebaseAuthRepository.requestOtp` (data layer) did
      `await _auth.verifyPhoneNumber(...); return completer.future;`. `verifyPhoneNumber` is
      **callback-driven** — `codeSent`/`verificationFailed` complete `completer` — but the method
      is `async`, so `return completer.future` (and therefore the whole `requestOtp` call) only
      runs once `verifyPhoneNumber`'s *own* returned `Future` resolves. On the
      emulator/test-number path that Future resolves promptly, which is why every prior
      automated/manual test passed. On the real-SMS path (iOS simulator's reCAPTCHA-webview
      fallback; macOS) that Future can stay pending long after `codeSent` already fired —
      trapping the already-completed `completer` behind the `await` and hanging `requestOtp`
      forever. The UI symptom (button spins, no navigation) matched item 16's bug 2 description,
      which led to that fix stopping short of finding this.
    - **Fix:** stop awaiting `verifyPhoneNumber`; fire it via `unawaited(...)` and let the
      `codeSent`/`verificationFailed` callbacks (unchanged) drive `completer`, funneling any
      Future-level failure through `.catchError` into the same completer (a `try/catch` around
      the call itself still covers a synchronous throw). `codeAutoRetrievalTimeout` and the
      Android-auto-retrieval no-op are unchanged.
    - **Why no test caught it originally:** every prior test (all 210 at the time) mocks
      `AuthRepository.requestOtp` at the interface, so the real `Completer` +
      `await verifyPhoneNumber` + callback plumbing was never exercised. Added a repo-level
      regression test (`firebase_auth_repository_test.dart`, `requestOtp` group) that stubs
      `verifyPhoneNumber` to invoke `codeSent` synchronously while returning a `Future` that
      never completes — reproducing the real-SMS shape. Verified this test genuinely fails
      (times out) against the pre-fix code and passes after, before treating it as done.
    - **Files:** `firebase_auth_repository.dart` (`requestOtp` only);
      `firebase_auth_repository_test.dart` (new `requestOtp` regression test).
